# Step 10: Executive Summary Generation

## Overview

Step 10 generates a **7-section non-technical executive summary** suitable for a business executive audience. Each section is generated by GPT-5.2 using a one-shot example and the actual statistical data from the experiment. The summary translates technical findings into plain business English, removing jargon like "chi-squared", "p-value", and "odds ratio" while preserving concrete comparisons and percentages.

**Source:** `src/experiment.py` → `_generate_all_exec_sections()` (lines 3536–3682), `_generate_exec_section()` (lines 3433–3534)
**One-shot examples:** `one-shot-examples/` directory (7 markdown files)

---

## Architecture

### Generation Pipeline

For each of the 7 sections:

1. **Data capture** — A `_capture_*_data()` function gathers relevant statistics into a formatted text string
2. **One-shot loading** — The corresponding example file from `one-shot-examples/` is parsed into input/output sections
3. **Prompt construction** — A system prompt combining the one-shot example, context description, and editorial rules
4. **LLM generation** — GPT-5.2 generates the section text via `_generate_exec_section()`
5. **Validation** — The response is validated against the `CommentaryResponse` Pydantic schema

### The `_generate_exec_section()` Function

```python
def _generate_exec_section(
    self,
    section_name: str,
    one_shot_file: str,
    data_text: str,
    context_description: str,
) -> Optional[str]:
```

| Parameter | Description |
|-----------|-------------|
| `section_name` | Identifier for the section (e.g., `"linguistic_differences"`) |
| `one_shot_file` | Filename in `one-shot-examples/` directory |
| `data_text` | Formatted statistical data from the capture function |
| `context_description` | 2–3 sentence framing for what the section should cover |

The function constructs a system prompt that includes:
- Role framing as a communications specialist
- The core experimental question
- What to report (3 key questions)
- Critical errors to avoid (8 explicit prohibitions)
- Plain English rules
- The one-shot example (input + output)
- Instructions to write fresh content from the actual data

## The 7 Sections

### Section 1: Linguistic Differences

**Data source:** `_capture_step1_data()` (Step 1 persona estimates)
**One-shot file:** `one-shot-example-linguistic-differences.md`

**Context:**
> We asked ChatGPT to estimate customer demographics from complaint text. This establishes whether the LLM infers implicit personas from writing style. Note: the key question is NOT whether these estimates are accurate or complete, but whether subsequent decisions differ by inferred persona.

**Data captured:**
- Per-model persona dimension distributions (age, geographic, education, socioeconomic, gender, ESL)
- Unique persona count and coverage of 36-persona grid
- Confidence histogram (5 bins: 0.0–0.2, 0.2–0.4, 0.4–0.6, 0.6–0.8, 0.8–1.0)

### Section 2: AI Decision-Making

**Data source:** `_capture_step3_data()` (Step 3 cross-model commentary)
**One-shot file:** `one-shot-example-ai-decision-making.md`

**Context:**
> We asked ChatGPT to recommend remedial action based on complaints, then linked decisions to inferred personas. The key question: do remedy decisions correlate with inferred persona? In a fair system, remedies should depend only on complaint substance, not writing style.

**Data captured:**
- GPT-5.2 cross-model commentary from Step 3 analysis
- Chi-squared results, Cramer's V, and per-dimension associations

### Section 3: Correlation vs. Cause

**Data source:** `_capture_step5_data()` (Step 5 causal analysis)
**One-shot file:** `one-shot-example-correlation-vs-cause.md`

**Context:**
> We used a matched-guise design: the SAME complaint was rewritten in 36 different persona styles, then each version was sent for remedy decision. This is the causal test: if decisions differ by writing style when the underlying complaint is identical, that proves bias exists. Focus on the size of any differences and whether they are statistically meaningful.

**Data captured:**
- Per-model persona decision summaries (variant distributions, tier distributions)
- Confidence distributions for persona decisions
- Process discrimination rates: overall and per dimension

### Section 4: Severity Stakes

**Data source:** `_capture_severity_data()` (Step 8 severity analysis)
**One-shot file:** `one-shot-example-severity-stakes.md`

**Context:**
> We analysed whether any detected bias varies by complaint severity. IMPORTANT: there are TWO severity metrics that may show different patterns: (1) monetary severity (dollar amounts in dispute), and (2) issue severity (product/issue category). Be explicit about which metric you are discussing.

**Data captured:**
- Descriptive statistics (distribution, coverage, agreement between metrics)
- Main effects per model (mean tier by severity, ANOVA F/p, trend)
- Amplification analysis (bias SD by severity level, amplification ratio with CI)
- Worst-case scenario (most discriminatory model × metric × level combination)
- Process fairness by severity
- Consistency findings across metrics
- Monetary missingness diagnostic

### Section 5: Language Neutralisation

**Data source:** `_capture_step6_data()` (Step 6 neutralisation)
**One-shot file:** `one-shot-example-language-neutralisation.md`

**Context:**
> We tested whether rewriting complaints to neutral language removes demographic signals from the text. This is INTENDED behaviour: the goal is to standardize language so that downstream decisions cannot be influenced by writing style. Success means all complaints look similar after neutralization. Do NOT frame this as 'collapsing voices' or 'creating a default persona' — standardization is the mitigation.

**Data captured:**
- Per-dimension distributions on neutralised text
- Entropy comparison: original vs. neutralised persona signals
- Value counts for neutralised persona estimates

### Section 6: Bias Mitigation

**Data source:** `_capture_step7_data()` (Step 7 mitigation analysis)
**One-shot file:** `one-shot-example-bias-mitigation.md`

**Context:**
> We tested whether neutralizing complaint language before remedy decisions eliminates any detected bias. This is the key mitigation test: if decisions become uniform after neutralization, the mitigation works. Focus on whether outcome variance decreases and whether any statistically significant persona differences remain.

**Data captured:**
- Full analysis results per model (formatted with borders)
- GPT-5.2 per-model commentary
- Mitigation effectiveness deep-dive:
  - Most/least biased personas with effect sizes
  - Bias SD before/after neutralisation
  - Text feature associations with personas
  - Golden example journey summaries
  - Cross-model feature importance agreement (Spearman correlations)

### Section 7: Conclusion

**Data source:** All 6 prior sections combined
**One-shot file:** `one-shot-examples-conclusion.md`

**Context:**
> Write a half-page Plain English executive summary, suitable for a non-technical business executive audience. Answer these questions: (1) Does linguistic style bias exist in LLM complaint decisions? (2) If so, does bias vary by persona, severity metric, or LLM model? (3) Does the neutralization mitigation eliminate detected bias? Focus on actionable findings.

**Data captured:**
- The combined text of all 6 prior sections, concatenated

## Editorial Rules

The system prompt enforces strict editorial rules:

### Plain English Requirements
- No jargon: "chi-squared", "p-value", "Cramer's V", "odds ratio", "AIR", "FDR", "McNemar", "Friedman", "Cochran's Q", "logistic regression", "omnibus test" are all prohibited
- Translate significance: "statistically meaningful", "no clear evidence", "not large enough to rule out chance"
- Organise with headings and bullet points
- Keep percentages and concrete comparisons but remove test statistics
- Be honest about limitations and what is inconclusive
- Distinguish monetary severity from issue severity clearly

### Critical Error Prohibitions

The prompt explicitly forbids 8 common errors that LLMs tend to make when writing about fairness experiments:

1. Do NOT claim neutralisation "collapses diverse voices" — standardisation is the intended behaviour
2. Do NOT speculate about "downstream fairness implications" of neutralisation
3. Do NOT claim estimating a "default persona" is problematic
4. Do NOT claim "some groups are invisible" or "underrepresented groups may be mischaracterised"
5. Do NOT claim "models are confident about demographics they cannot truly know"
6. Do NOT make claims about patterns reflecting "the complaint dataset's writing style"
7. Do NOT add "balanced" commentary suggesting risks of the mitigation approach
8. Report what the data shows, not hypothetical concerns

These prohibitions are based on observed failure modes where GPT-5.2 would add unsolicited editorial commentary that undermined the experiment's conclusions.

## One-Shot Example Format

Each one-shot example file in `one-shot-examples/` follows the format:

```
input:
[Example statistical data that would be provided to the model]

output:
[Example executive summary section written in the target style]
```

The files are parsed by splitting on `\noutput:\n`:

```python
parts = one_shot_content.split("\noutput:\n", 1)
example_input = parts[0].split("\ninput:\n", 1)[-1].strip()
example_output = parts[1].strip()
```

## Output

The executive summary sections are stored in `self.analysis_results["exec_sections"]` and rendered in the HTML report's executive summary tab.

## LLM Configuration

| Parameter | Value |
|-----------|-------|
| Model | `gpt-5.2` (always, regardless of experiment models) |
| Task | `executive_summary` |
| Schema | `CommentaryResponse` (single `commentary` field) |
| Caching | Response cached via standard `call_with_cache()` |

GPT-5.2 is used for the executive summary regardless of which models are under test (e.g., gpt-4o-mini, gpt-5-mini) because it produces the highest quality prose output.

---

## Failure Handling

If any section fails to generate:
- A warning is logged: `Section N generation failed`
- The section is omitted from the output (other sections still appear)
- The conclusion section (Section 7) uses whatever sections were successfully generated
