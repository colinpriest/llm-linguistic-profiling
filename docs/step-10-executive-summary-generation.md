# Step 10: Executive Summary Generation

## Overview

Step 10 generates a **multi-section non-technical executive summary** suitable for a business executive audience. Each section is generated by GPT-5.2 using a one-shot example and the actual statistical data from the experiment. The summary translates technical findings into plain business English, removing jargon like "chi-squared", "p-value", and "odds ratio" while preserving concrete comparisons and percentages.

The generator produces **9 sections** (8 displayed with headings + 1 internal bridging section used as input to the conclusion). The sections cover the full experimental pipeline: persona estimation, decision-making, causal testing, severity amplification, neutralisation, mitigation, data quality, and a synthesis conclusion.

**Source:** `src/experiment.py` → `_generate_executive_summary()` (line 4327), `_generate_all_exec_sections()` (line 4393), `_generate_exec_section()` (line 4224)
**One-shot examples:** `one-shot-examples/` directory (8 markdown files)

---

## Architecture

### Execution Ordering

The executive summary is generated **after** all analyses are complete, including the robustness subset analysis. This ensures all data is available:

```
run()
  → _run_slot_audit()              # produces slot audit metrics
  → _run_analyses()                # produces all statistical analyses
  → _save_artifacts()              # writes CSVs and JSON
  → _run_robustness_subsets()      # produces robustness subset verdicts
  → _generate_executive_summary()  # generates all exec sections (needs all data above)
```

The `_generate_executive_summary()` method:
1. Calls `_generate_all_exec_sections()` to produce all 9 sections
2. Stores sections in `self.analysis_results["exec_sections"]`
3. Writes the standalone text file `executive_summary_{timestamp}.txt`
4. Re-writes the `analysis_results_{timestamp}.json` to include exec sections

### Generation Pipeline

For each section:

1. **Data capture** — A `_capture_*_data()` function gathers relevant statistics into a formatted text string
2. **One-shot loading** — The corresponding example file from `one-shot-examples/` is parsed into input/output sections
3. **Prompt construction** — A system prompt combining the one-shot example, context description, and editorial rules
4. **LLM generation** — GPT-5.2 generates the section text via `_generate_exec_section()`
5. **Validation** — The response is validated against the `CommentaryResponse` Pydantic schema
6. **Caching** — Each section is cached via `call_with_cache()` with variant `exec_{section_name}`

### The `_generate_exec_section()` Function

```python
def _generate_exec_section(
    self,
    section_name: str,
    one_shot_file: str,
    data_text: str,
    context_description: str,
) -> Optional[str]:
```

| Parameter | Description |
|-----------|-------------|
| `section_name` | Identifier for the section (e.g., `"linguistic_differences"`) |
| `one_shot_file` | Filename in `one-shot-examples/` directory |
| `data_text` | Formatted statistical data from the capture function |
| `context_description` | 2–3 sentence framing for what the section should cover |

The function constructs a system prompt that includes:
- Role framing as a communications specialist
- The core experimental question
- What to report (3 key questions)
- Critical errors to avoid (8 explicit prohibitions)
- Plain English rules
- The one-shot example (input + output)
- Instructions to write fresh content from the actual data

## The 9 Sections

### Section 1: Linguistic Differences

**Data source:** `_capture_step1_data()` (Step 1 persona estimates)
**One-shot file:** `one-shot-example-linguistic-differences.md`
**Cache variant:** `exec_linguistic_differences`

**Context:**
> We asked ChatGPT to estimate customer demographics from complaint text. This establishes whether the LLM infers implicit personas from writing style. Note: the key question is NOT whether these estimates are accurate or complete, but whether subsequent decisions differ by inferred persona.

**Data captured:**
- Per-model persona dimension distributions (age, geographic, education, socioeconomic, gender, ESL)
- Full persona label counts (36-persona grid coverage)
- Unique persona count per model
- Confidence histogram (5 bins: 0.0–0.2, 0.2–0.4, 0.4–0.6, 0.6–0.8, 0.8–1.0)

### Section 2: AI Decision-Making

**Data source:** `_capture_step3_data()` (Step 3 cross-model commentary)
**One-shot file:** `one-shot-example-ai-decision-making.md`
**Cache variant:** `exec_ai_decision_making`

**Context:**
> We asked ChatGPT to recommend remedial action based on complaints, then linked decisions to inferred personas. The key question: do remedy decisions correlate with inferred persona? In a fair system, remedies should depend only on complaint substance, not writing style.

**Data captured:**
- GPT-5.2 cross-model commentary from Step 3 analysis (the `step3_commentary` string)
- This is the pre-generated statistical commentary containing chi-squared results, Cramer's V, and per-dimension associations

### Section 3: Correlation vs. Cause

**Data source:** `_capture_step5_data()` (Step 5 causal analysis)
**One-shot file:** `one-shot-example-correlation-vs-cause.md`
**Cache variant:** `exec_correlation_vs_cause`

**Context:**
> We used a matched-guise design: the SAME complaint was rewritten in 36 different persona styles, then each version was sent for remedy decision. This is the causal test: if decisions differ by writing style when the underlying complaint is identical, that proves bias exists. Focus on the size of any differences and whether they are statistically meaningful.

**Data captured:**
- Per-model persona decision summaries:
  - Top 10 persona × tier crosstab
  - Mean tier by each causal dimension (age, geographic, education, socioeconomic)
  - Overall tier distribution
- Process discrimination rates:
  - Overall info request rate (`need_more_info` proportion)
  - Info request rate by each causal dimension

### Section 4: Severity Stakes

**Data source:** `_capture_severity_data()` (severity analysis results)
**One-shot file:** `one-shot-example-severity-stakes.md`
**Cache variant:** `exec_severity_stakes`

**Context:**
> We analysed whether any detected bias varies by complaint severity. IMPORTANT: there are TWO severity metrics that may show different patterns: (1) monetary severity (dollar amounts in dispute), and (2) issue severity (product/issue category). Be explicit about which metric you are discussing. If one shows amplification and the other does not, state this clearly without contradiction.

**Data captured:**
- Severity metrics overview:
  - Distribution per metric (low/medium/high/unknown counts)
  - Coverage rate (% with extractable dollar amounts)
  - Agreement between monetary and issue severity (Cohen's kappa, Spearman r, agreement rate)
- Main effects per model:
  - Mean tier by severity level
  - One-way ANOVA (F, p-value, partial eta-squared)
  - Spearman monotonic trend test
- Amplification analysis per model × metric:
  - Bias SD at each severity level (low/medium/high)
  - Amplification ratio with bootstrap CI
  - Two-way interaction (persona × severity) ANOVA
- Worst-case scenario (most discriminatory model × metric × level combination with Cohen's d)
- Process fairness (info request disparity by severity level)
- Consistency findings across metrics
- Monetary missingness diagnostic (MCAR/MAR pattern, affected dimensions)

### Section 5: Language Neutralisation

**Data source:** `_capture_step6_data()` (Step 6 neutralisation results)
**One-shot file:** `one-shot-example-language-neutralisation.md`
**Cache variant:** `exec_language_neutralisation`

**Context:**
> We tested whether rewriting complaints to neutral language removes demographic signals from the text. This is INTENDED behaviour: the goal is to standardize language so that downstream decisions cannot be influenced by writing style. Success means all complaints look similar after neutralization. Do NOT frame this as 'collapsing voices' or 'creating a default persona' — standardization is the mitigation.

**Data captured:**
- Per-model neutralised persona re-estimates:
  - Distribution of each dimension (age, geographic, education, socioeconomic, gender, ESL) after neutralisation
- Entropy comparison: original vs neutralised persona signals per dimension
  - Lower entropy after neutralisation = stronger demographic signal collapse (desired outcome)

### Section 6: Bias Mitigation

**Data source:** `_capture_step7_data()` (Step 7 analysis + mitigation effectiveness deep-dive)
**One-shot file:** `one-shot-example-bias-mitigation.md`
**Cache variant:** `exec_bias_mitigation`

**Context:**
> We tested whether neutralizing complaint language before remedy decisions eliminates any detected bias. This is the key mitigation test: if decisions become uniform after neutralization, the mitigation works. Focus on whether outcome variance decreases and whether any statistically significant persona differences remain.

**Data captured (two parts):**

**Part 1 — Per-model analysis results:**
- Full formatted analysis results per model (from `_format_results_for_commentary()`)
- GPT-5.2 per-model commentary

**Part 2 — Mitigation effectiveness deep-dive** (from `_capture_mitigation_effectiveness_data()`):
- Feature importance from neutralisation models:
  - Top features predicting tier change after neutralisation (with R² scores)
  - Mixed-effects model significant coefficients
- Causal persona effects:
  - Which dimension changes most affect tier assignment
  - Feature importance ranked by effect on tier
- Heterogeneous treatment effects:
  - Average Treatment Effect (ATE) with CI
  - Important moderating variables
  - Subgroup conditional ATEs (top 5)
- Golden example:
  - Single complaint tracked through full pipeline
  - Estimated persona, original tiers, neutralised tiers per model
  - Tier variance across personas, neutralisation effect
  - Best and worst outcome personas
- Supporting examples (selected illustrative cases)
- Cross-model feature importance agreement (Spearman rho)

### Section 7: Bridging Commentary (internal)

**Data source:** `_capture_bridging_data()` (text features → persona → outcomes)
**One-shot file:** `one-shot-example-bridging-commentary.md`
**Cache variant:** `exec_bridging_text_to_outcome`

**Context:**
> This section connects three layers of evidence from the experiment: (i) observable text characteristics that predict persona assignment, (ii) the persona labels themselves, and (iii) how those labels relate to remedy tier outcomes and tier dispersion. Use association / consistency language (not causal claims). Keep it to 2-3 paragraphs.

**Data captured:**
- Per-model top text features predicting persona dimensions:
  - Feature display name, importance score, AUC for each dimension=value combination
  - Summary strings explaining the association
- Tier 2 rates by persona dimension (from correlation analysis)
- Cross-model feature importance agreement (Spearman rho between model pairs)

**Note:** This section is generated and included in the `sections` dict but does **not** have its own heading in the output text file. It is consumed as input to the Conclusion section via `combined_sections = "\n\n".join(sections.values())`. Its purpose is to provide the conclusion with a richer textual bridge between text features, persona labels, and outcomes.

### Section 8: Robustness & Data Quality

**Data source:** `_capture_robustness_data()` (slot audit + robustness subset analysis)
**One-shot file:** `one-shot-example-robustness-quality.md`
**Cache variant:** `exec_robustness_quality`

**Context:**
> This section reports on the quality of the matched-guise experimental data and whether the causal findings are robust to filtering on data quality. The slot-preservation audit checks that persona-rewritten complaints preserved the factual content (amounts, dates, claim polarity, named entities) of the original. The robustness subset analysis tests whether restricting to high-fidelity pairs attenuates or amplifies the observed persona effects. Focus on whether the findings can be trusted and what the quality checks imply.

**Data captured (two parts):**

**Part 1 — Slot-preservation audit:**
- Total matched-guise pairs and complaints
- Viability gate result (PASS/FAIL) with all 6 threshold checks:
  - High-fidelity pair rate, high-fidelity complaint rate
  - Polarity contradiction rate, numeric mutation rate
  - Temporal presence preservation, anchor presence preservation
- Per-family preservation rates (numeric, temporal, polarity, anchor) with CIs
- Per-model comparison (pairs, strict pass rate, hi-fi rate, contradiction rate)

**Part 2 — Robustness subset analysis:**
- Overall verdict (PASS / PASS_WITH_CAUTION / FAIL)
- Subset aliases (e.g., HF_NO_POL aliased to HF)
- Effect stability vs FULL baseline:
  - Per subset × model × effect: attenuation, direction (stable/amplified/attenuated), CI overlap
- Outcome composition shift:
  - Per model: mean tier of kept vs dropped pairs, bias direction (anti-conservative/conservative/neutral)

### Section 9: Conclusion

**Data source:** All 8 prior sections combined (including bridging commentary)
**One-shot file:** `one-shot-examples-conclusion.md`
**Cache variant:** `exec_conclusion`

**Context:**
> Write a half-page Plain English executive summary, suitable for a non-technical business executive audience. Answer these questions: (1) Does linguistic style bias exist in LLM complaint decisions? (2) If so, does bias vary by persona, severity metric, or LLM model? (3) Does the neutralization mitigation eliminate detected bias? Focus on actionable findings. Avoid tangential commentary about 'invisible groups', 'default personas', or persona estimation accuracy.

**Data captured:**
- The concatenated text of all 8 prior sections (including the bridging commentary)

## Editorial Rules

The system prompt enforces strict editorial rules:

### Plain English Requirements
- No jargon: "chi-squared", "p-value", "Cramer's V", "odds ratio", "AIR", "FDR", "McNemar", "Friedman", "Cochran's Q", "logistic regression", "omnibus test" are all prohibited
- Translate significance: "statistically meaningful", "no clear evidence", "not large enough to rule out chance"
- Organise with headings and bullet points
- Keep percentages and concrete comparisons but remove test statistics
- Be honest about limitations and what is inconclusive
- Distinguish monetary severity from issue severity clearly

### Critical Error Prohibitions

The prompt explicitly forbids 8 common errors that LLMs tend to make when writing about fairness experiments:

1. Do NOT claim neutralisation "collapses diverse voices" — standardisation is the intended behaviour
2. Do NOT speculate about "downstream fairness implications" of neutralisation
3. Do NOT claim estimating a "default persona" is problematic
4. Do NOT claim "some groups are invisible" or "underrepresented groups may be mischaracterised"
5. Do NOT claim "models are confident about demographics they cannot truly know"
6. Do NOT make claims about patterns reflecting "the complaint dataset's writing style"
7. Do NOT add "balanced" commentary suggesting risks of the mitigation approach
8. Report what the data shows, not hypothetical concerns

These prohibitions are based on observed failure modes where GPT-5.2 would add unsolicited editorial commentary that undermined the experiment's conclusions.

## Output

### In-Report Display

The executive summary sections are stored in `self.analysis_results["exec_sections"]` (a dict mapping section keys to text) and `self.analysis_results["business_executive_summary"]` (all sections concatenated). These are rendered in the HTML report's executive summary tab.

### Standalone Text File

All 8 displayed sections are saved as a standalone text file:

```
============================================================
BUSINESS EXECUTIVE SUMMARY (8 SECTIONS)
============================================================

──────────────────────────────────────────────────
SECTION 1: LINGUISTIC DIFFERENCES
──────────────────────────────────────────────────
[Section 1 text]

──────────────────────────────────────────────────
SECTION 2: AI DECISION-MAKING
──────────────────────────────────────────────────
[Section 2 text]

... (all 8 displayed sections) ...

============================================================
```

Output path: `output/executive_summary_{timestamp}.txt`

The same format is also written by `src/paper_bundle.py` to the evidence folder when generating the paper bundle.

### Analysis Results JSON

After the executive summary is generated, the `analysis_results_{timestamp}.json` file is **re-written** to include the `exec_sections` dict. This ensures the JSON artifact contains the full experiment output including the generated prose.

## LLM Configuration

| Parameter | Value |
|-----------|-------|
| Model | `gpt-5.2` (always, regardless of experiment models) |
| Task | `executive_summary` |
| Schema | `CommentaryResponse` (single `commentary` field) |
| Temperature | Omitted (reasoning model — API rejects this parameter) |
| Max completion tokens | `32,000` (reasoning model budget) |
| Caching | Response cached via `call_with_cache()` keyed by variant |

GPT-5.2 is used for the executive summary regardless of which models are under test (e.g., gpt-4o-mini, gpt-5-mini) because it produces the highest quality prose output. As a reasoning model, it does not accept the `temperature` parameter.

---

## Failure Handling

If any section fails to generate:
- A warning is logged: `Section N generation failed`
- The section is omitted from the output (other sections still appear)
- The conclusion section uses whatever sections were successfully generated
- The bridging section failing is non-fatal — the conclusion simply has less context
